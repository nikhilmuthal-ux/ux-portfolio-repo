Context and problem

When a run fails, the operator has to find it, understand it and act.

  1. 1Equal weight everywhere
  2. 2Too many jumps to diagnose one run
  3. 3No clear executed path
  4. 4Unlabeled icons

Problem statement

How might we take an operator from a failed run to its cause, on one screen?

04

Shaping the solution

Four principles, tested against real content.

Design principles

01

Visual weight follows priority

Status and name first, rare actions quiet.

02

One screen, no page jumps

Everything updates in place.

03

Color means status

Green, red, amber, blue. Nothing else.

04

Every control explains itself

Labels, tooltips and full states.

From early iteration to Phase 1

An early version was developed and reviewed every week. Each round moved it closer to the final screen.

Process list

Names only Status, time and a duration bar for every run.

Filters

Dropdowns, dates and Apply Status filters with counts, one click.

Diagram

Dense black arrows Executed path in green, failure in red.

Details

Raw configuration text Grouped tables; tabs follow the activity.

Decisions I revisited

Toolbar

One clear row with grouped controls.

Attributes

A tag button in the toolbar, hidden by default.

Layout stability

Equal split and fixed card heights. Nothing jumps.
